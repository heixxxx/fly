## 问题 1：park 闸门 SIGSTOP 投递窗口竞争（测试时序缺陷）

**轮次**：round 4 / 100（`test_wait_death_linkage.pyt`，唯一失败 case）。

**现场**（`qa/fault/test_wait_death_linkage/1_wait_linkage_run2/master.log`）：

```
09:04:18.274 Worker registered: worker_id=1, hostname=link-host-1
09:04:18.351 [linkage] parked worker pid=29133 (SIGSTOP) before load_db
09:04:18.352 Sent IdxLoadCommand to worker_id=1
09:04:18.353 IdxLoadAck: worker_id=1, success=true, loaded_count=1   ← STOP 后 2ms！
09:04:48.398 worker 1 offline（= 18.351 + 30.047s 心跳超时判死）      ← STOP 最终生效
```

测试断言 `idx_load_pending == 1` 30s 超时失败（load_db 早已成功返回）。

**根因**：`os.kill(pid, SIGSTOP)` 的信号投递是**异步**的——kill 返回时目标
进程未必已停。本例中 worker 在停止生效前的毫秒窗口内处理完 IdxLoad 并回了
ack，可见性屏障瞬间归零；而 30s 后心跳超时判死证明 STOP 确实生效了（进程
最终停了，只是"何时停"不确定）。park 闸门（"冻结 worker 使屏障稳定
pending==1"）不成立，本质与它要替代的"杀 worker 时序竞争"同构。

**修复**（`qa/fault/wait_linkage_run2.py`）：STOP 后轮询 `/proc/{pid}/stat`
的进程状态直到 `T`（job-stopped，SIGSTOP 不可捕获/忽略，状态必然到达），
park 才是确定性闸门：

```python
os.kill(proc.pid, signal.SIGSTOP)
while True:
    state = open(f"/proc/{proc.pid}/stat").read().rsplit(") ", 1)[1].split()[0]
    if state == "T":
        break
    time.sleep(0.01)
```

**验证**：单 case 连跑 10/10 通过；重启 100 轮全程无复现（含本 case 的
100 次执行）。

**教训**：SIGSTOP/SIGKILL 的 kill 返回点不是进程状态变更点——一切"停了再
断言"的测试构造必须以 `/proc` 状态为准（与 `expect 必须在 Popen 前` 同属
"进程状态与观察点之间必须显式同步"一族）。
