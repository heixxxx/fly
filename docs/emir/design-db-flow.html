层级树与全局编号：起始编号段分配

对应章节：§2.2「编号（id）体系」 与 §2.5「层级模型：block 与 block instance」

鼠标悬停树上任一 block instance 节点（或下方编号段条的分段），对应编号段互相高亮。

编号区间表（保存在 hierarchy tree 结构中，裁定 ⑮；示意数值，四段连续相接、无空洞）

instance 编号空间，总覆盖 [0, 1300)（深度优先序分配）
net 编号空间，总覆盖 [0, 117)（深度优先序分配）

hierarchy tree 四类接口（裁定 ⑮）

① 查询某个 instance/net id 所属的 block instance（区间反查） ② 查询某个 block instance 的 instance/net id 范围 ③ 查询某个 block instance 的 parent id 与直系 child id 列表 ④ 打印 hierarchy tree（以 name 表示——node 同时存 name 与 id）

每个 block instance 一段连续区间，区间长度 = 该 block 定义的 instance / net / via instance 计数。计数由 S5a 的两并行任务产生（任务一实例侧 / 任务二网名扫描侧），起始编号在层级树构建（S6，与 S5b 并行——均仅依赖 S5a，裁定 ⑨）时分配——两阶段解耦，local id 无需跨任务协调；S5b 产物为 local net id（per-DEF 解析尚未 flatten，无法得全局 id），instance / net / via instance 三类 global id 统一在 S9 flatten 展开时按 local id + 起始编号换算。编号保留语义（裁定 ⑧）：leaf instance 的 local id 从 1 起，local 0 = 当前 block 自身占位（展开时映射为该 block instance 的 global id）；global id 0 = top block instance（树根）。S10 校验项：global id 无空洞重复。

global id 换算示例

global id = 所属 block instance 起始编号 + block 内 local id

示例 1 · 同一定义、不同实例 → 编号段复制

block instance A 内 local instance id = 250 global = 100（A 起始） + 250 = 350 block instance B 内 local instance id = 250 global = 800（B 起始） + 250 = 1050 （A 与 B 引用同一 block 定义 D1， 存储单份，编号段复制两份）

示例 2 · 跨层网编号（衔接板块 5 的并查集示例）

top 内网 VDD：local net id 5 global net id = 0 + 5 = 5 block instance A 内网 VDD：local 0 global net id = 12 + 0 = 12 block instance A1 内网 VDD：local 0 global net id = 52 + 0 = 52

示例 3 · 编号保留语义（裁定 ⑧）

block instance A 内 local instance id 0（自身占位） global = 100 + 0 = 100 = A 的 global id top 的 local 0 → global id 0 = top block instance（树根） leaf instance 的 local id 从 1 起

关键澄清：block（定义）层面是有向无环图（同一 block 定义被多处引用是设计常态，如一个接口单元 block 放置上百次）；block instance（实例）层面才是树——每个实例恰有一个父。原始数据绝不按实例复制存储，多实例只体现在编号空间与分区切分产物中。

将鼠标移到左侧任一图形上（或点击），这里将显示其定位点坐标与逐步判定。

统一判定语义

每个分区为半开区间 [x_min, x_max) × [y_min, y_max) 定位点 px ∈ [x_min, x_max) 即归属 图形左下角所在分区 = 该数据的主分区 图形实体（不裁剪，裁定 D8）同时登记到 所有与其交叠的分区 = 普通分区

叶实例：逻辑归属（连接、cell 引用、电源引脚坐标）归锚点分区 = 实例左下角主分区；实例图形按各自定位点散布到交叠分区（裁定 D7）。块实例本身不作为切分单位——大 block 的内部数据天然跨分区，正合原始需求「block1 横跨两分区」的场景。

union 依据与补充说明

  • union 依据完全来自已有连接数据：父网 connection（网侧连接条目）中的条目（块实例 id, port pin id, 父网 net id）+ 子网条目（连接该 port 的子网 local net id），两侧经 port pin id 对接。
  • 同一子网连接多个 port、且这些 port 在父层连到不同父网 → 两父网亦被 union（电气等价，合法形态）。
  • ☆ root → 成员索引（本文补充）：原始需求只有正向 find；物理网（如 VDD）的全部成员枚举是 ④⑤⑥ 按「物理网」聚合消费的前提——由父表按 root 分组导出并持久化。
  • 顶层引脚连接（DEF 中 ( PIN portName ) 语法）：顶层网直接挂顶层 port，作为 root 候选；悬空 port（未连接任何父网）计数提醒，不 raise。

实现期约束与前置工具（裁定 ㉒/㉓）

  • geometry 独立通用子模块（裁定 ㉑）：Point / Rect / Polygon 模板及几何配套（变换 / 面积 / 交叠运算）不属 design 模块内部结构，独立成通用子模块供下游多业务复用（design db、④ 提取、几何分析等）；归属路径与命名前缀见裁定 D28（建议 src/container/geometry/ + CM 前缀，与 CMLookupTable 同体系）。
  • 存储形态逐字段决策（裁定 ㉒）：实现时对每个结构、每个字段分析 ptr 还是直接存对象——目标是减少 copy 与防止不期望的连锁修改（ptr 共享则一处修改处处可见）；直接存对象更快更省内存时（小对象 / 拷贝便宜 / 无共享需求）就直接存对象，否则按数据使用与搬移情况用 ptr；禁止使用裸指针（拥有关系用 CMSharedPtr / CMUniquePtr，观察传参用引用）。
  • CM_PROPERTY 宏（裁定 ㉓）——待本文档批准后实施（全仓库当前不存在该宏）：属公共工具宏（非 container 模块），拟放置 src/common/types/cpp/property_macro.h（公共宏归 common 模块族，同 FLY_SERIALIZE_* 宏族先例；纯头仅依赖 <utility>，随 fly_common_types 轻量库；不放 container——container_aliases.h 聚合全部容器头与指针别名，仅为一个宏引入过重的头文件依赖）。用法 CM_PROPERTY(attr_name); 自动生成 get_attr_name / get_ref_attr_name / get_cref_attr_name / set_attr_name / set_attr_name_move 五个接口；要求成员变量以 _ 结尾。

connection（连接）双索引组织（§2.3）：connection 本体是三元组（instance id, pin id, net id），按两种主键各建一份索引——InstConnection（instance id 主键，实例侧聚集：⑩⑪ 逐实例电流；跨块 port 连接三元组的 instance 端用 local 0 = block 自身占位，裁定 ⑧）与 NetConnection（net id 主键，网侧聚集：④ 网几何归属、⑫ 注入点）。独立编号空间（§2.2，裁定 ⑩）：layer id、cell id（含 block cell id）、pin id（含 port id）、via cell id（独立类型，非 cell 特例；DEF 来源登记名带 design 名:: 前缀，全集集中保存为单一权威表，裁定 ⑫）、instance id、net id、via instance id（专用独立空间，非 instance、无 name 不入 namemap）——layer / cell / pin / via cell 为全局一次分配，instance / net / via instance 为 block 内 local id → global id（S9 展开时换算）。DSDesign 容器（裁定 ⑬）：全局且相对轻量的数据（cell 单一结构 / 简化 pin / via cell 权威表 / lib 关联 / 层级树含编号区间表 / 轻量 namemap）统一入容器，后续功能（查询、索引、派生数据）经增强该类完成；layer 例外为独立 Stack 类型（裁定 ⑭）——层堆栈结构跨 design db / tech db 复用；instance/net 的 name 映射、块内原始数据、并查集、分区产物、密度图为独立对象，不进容器。pin 存储简化（裁定 ⑰/⑱）：DSDesign 序列化内容仅含简化 pin（类型 / 方向等基础属性）；pin 表数据与 pin 几何数据为两个独立对象（cell 的两个不序列化字段），业务方按需经统一加载 API（load + set 封装）注入，下游一律经 get_cell 按指针零拷贝获取；fake cell（裁定 ⑲/⑳）以单独字段保存，区别于正常 cell。
