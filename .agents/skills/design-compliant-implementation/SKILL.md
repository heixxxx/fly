# 技能：高质量设计合规实现

## 技能描述
代码实现需高质量完成、符合设计优先，禁止由于实现困难而切换至简单但是不符合设计要求的方法。如遇到无法/难以解决的问题，列出问题后咨询用户。

## 核心原则

```
PRINCIPLE 1: 设计优先
  设计文档 > 实现便利性
  架构一致性 > 局部最优
  长期可维护性 > 短期省事

PRINCIPLE 2: 不降级
  遇到实现困难时，禁止选择不符合设计的"简单方案"
  禁止使用 workaround / hack / 技术债 来绕过设计约束
  禁止以"后面再优化"为理由接受不合规的实现

PRINCIPLE 3: 咨询而非放弃
  遇到真正的技术障碍时：
  1. 列出所有具体问题
  2. 分析根本原因
  3. 提出替代方案（需符合设计精神）
  4. 咨询用户决策
```

## 禁止的行为

```
❌ 因实现复杂就违背设计文档
   设计: "Config使用单例模式"
   实现时: "单例太麻烦，改成全局变量吧" → ❌

❌ 使用技术债换取短期便利
   "这里先hardcode，后面再抽象" → ❌

❌ 绕过程序正确性保障
   使用 @ts-ignore / as any / 空catch绕过程序正确性保障 → ❌

❌ 降低测试标准
   跳过测试 / 删掉失败测试 / 降低覆盖率阈值 → ❌

❌ 选择性遵循设计
   只实现设计的"简单部分"，忽略核心约束 → ❌
```

## 工作流程

### 1. 理解设计
```
1.1 阅读设计文档，理解核心意图
   - 设计要解决什么问题？
   - 为什么选择这个方案？
   - 关键约束是什么？

1.2 识别设计的核心约束 vs 实现细节
   - 核心约束：必须严格遵守的架构决策
   - 实现细节：可以灵活调整的具体方式

1.3 确认理解
   - 总结设计意图给用户确认
   - 如有疑问，在开始前澄清
```

### 2. 评估实现难度
```
2.1 初步评估
   - 分析实现路径
   - 识别风险和难点
   - 估算工作量和依赖

2.2 如果感觉困难：
   - 先分解问题：具体卡在哪里？
   - 区分"真正的困难" vs "单纯复杂"
   - 查资料/找参考，看别人怎么解决
   - 尝试原型验证最危险的部分
```

### 3. 决策树
```
遇到实现困难时：

3.1 困难是可分解的？
   ✅ → 分解成小步骤，逐一解决
   ❌ → 进入 3.2

3.2 困难可通过学习/调研解决？
   ✅ → 查阅文档/源码/示例
   ❌ → 进入 3.3

3.3 困难是真正的技术障碍？
   ✅ → 进入步骤4：咨询用户
   ❌ → 重新评估，可能只是复杂而非困难
```

### 4. 咨询用户（当需要时）
```
模板：

问题报告：
- 当前实现目标：[具体要实现什么]
- 设计约束：[设计文档中的核心要求]
- 遇到的障碍：[具体卡在哪]
- 已尝试的解决方式：[尝试了哪些方案]
- 根本原因：[为什么这些方案不行]

选项分析：
- 选项A（推荐）：[方案描述，优缺点]
- 选项B（备选）：[方案描述，优缺点]
- 选项C（降级方案，仅在设计中允许）：[方案描述，影响]
- 选项D（修改设计）：[需要改什么，影响]

请用户决策：[具体需要用户抉择的问题]
```

## 示例场景

### 场景1：C++模板元编程复杂度
```
设计: 使用C++模板实现编译期类型派发
遇到: 模板嵌套导致编译错误，很难调试

正确做法:
1. 分析模板错误原因
2. 尝试简化模板结构但不改变接口
3. 如仍不行，列出具体问题给用户：
   "模板实例化深度超过编译器限制（gcc12），
    选项A：分拆模板为更小单元（推荐）
    选项B：改用运行时多态（违反设计意图）
    选项C：升级编译器/放宽限制"

错误做法:
"模板太难用了，直接改成虚函数吧" → ❌
```

### 场景2：nanobind绑定复杂类型
```
设计: 使用FLY_EXPORT_*宏导出复杂嵌套类型
遇到: nanobind序列化嵌套类型有坑

正确做法:
1. 查nanobind文档/源码
2. 尝试不同写法
3. 仍不行则咨询用户：
   "FLY_EXPORT_SERIALIZE对嵌套CMVector<CMMap<...>>序列化失败
    因为bitsery/nanobind对深层嵌套的type erasure支持有限
    选项A：为嵌套类型手写__getstate__/__setstate__
    选项B：简化导出类型层级
    方案C：改用pybind11（需修改FLY_EXPORT_*宏）"

错误做法:
"导出太麻烦，用pickle绕过吧" → ❌
```

### 场景3：分布式一致性保证
```
设计: 实现两阶段提交保证数据一致性
遇到: 网络分区时状态难以判断

正确做法:
1. 分析网络分区场景
2. 查分布式系统文献/现有方案
3. 仍不行则咨询用户：
   "网络分区时，Worker断开连接后Master无法区分
   '任务失败'和'还没完成'
    选项A：加入超时重试+状态查询机制（推荐）
    选项B：简化为一阶段提交（降低一致性保证）
    选项C：引入共识算法（增加复杂度）"

错误做法:
"网络分区太复杂，直接返回成功就行" → ❌
```

## 质量验收标准

```
✅ 实现完全符合设计文档的接口和语义
✅ 没有因"省事"而引入的技术债或workaround
✅ 所有测试通过（包括新增的和已有的）
✅ 代码风格与项目现有代码一致
✅ 无类型错误、无lint警告、无未处理异常
✅ 如果咨询过用户，按照用户决策执行

❌ 不接受：跳过测试、忽略错误、使用技术债
❌ 不接受：因实现困难而改变核心设计
❌ 不接受：没有咨询用户就自行降级
```
