# 技能：系统化调试 - 多维度分析法

## 技能描述
本技能强调在调试时需要结合代码流程、架构、运行结果及日志来共同分析问题。若日志覆盖不足，则增加日志后重新运行测例来获取更多信息，避免仅通过代码静态分析问题。

## 核心原则
- **多维度分析**：必须结合代码、日志、运行结果、架构设计共同调试
- **数据驱动**：通过运行时日志和测试结果获得真实数据，而非仅靠代码推理
- **增量式调试**：日志不足时，先增加日志，再运行测试获取新信息
- **架构导向**：理解分布式架构的特性，从Master/Worker交互角度分析问题

## 适用场景
- 分布式系统的网络通信问题
- 多线程并发和同步问题
- 任务调度和依赖管理问题
- 数据存储和访问问题
- 跨语言（C++/Python）交互问题
- 性能瓶颈和资源泄漏问题

## 调试工作流程

### 1. 问题识别与分类
```
1.1 问题定位
   - 确定问题发生在哪个组件（Master/Worker/Network/Storage）
   - 识别问题类型（网络/内存/逻辑/并发）
   - 确定复现条件和环境

1.2 问题分类
   - 按组件：Master Agent、Worker Agent、Network、Storage、Task
   - 按性质：网络连接、数据传递、任务执行、资源管理
   - 按层级：C++层、Python层、C++/Python边界
```

### 2. 多维度数据收集
```
2.1 代码流程分析
   - 调用链追踪：从问题点回溯到调用起点
   - 数据流分析：数据在组件间的传递路径
   - 生命周期分析：组件的创建、使用、销毁过程

2.2 运行时日志收集
   - Master日志：master.log - 任务调度、Worker管理、元数据操作
   - Worker日志：worker{N}.log - 任务执行、数据操作、心跳发送
   - 网络日志：连接状态、消息传递、错误响应
   - 时间戳分析：操作顺序和时序问题

2.3 架构上下文分析
   - Master-Worker交互模式：注册、心跳、任务分配
   - 数据存储访问模式：本地vs远程、并发访问控制
   - 任务依赖管理：依赖图构建和调度策略
```

### 3. 日志增强策略
```
3.1 日志覆盖不足时的处理
   3.1.1 识别关键路径
      - 找到问题相关的代码路径
      - 确定需要监控的操作点
      - 选择合适的日志级别

   3.1.2 添加诊断日志
      void MasterAgent::assign_task_to_worker(uint64_t task_id, uint64_t worker_id) {
          DEBUG_LOG("MasterAgent", "Assigning task " << task_id << " to worker " << worker_id);
          DEBUG_LOG("MasterAgent", "Worker state before assignment: " << worker_manager_->get_worker_state(worker_id));
          // 原有逻辑
          DEBUG_LOG("MasterAgent", "Task assignment completed for task " << task_id);
      }

   3.1.3 日志记录规范
      - 组件前缀："[MasterAgent] ", "[WorkerAgent] ", "[Network] ", "[Storage] "
      - 时间戳：自动包含，便于时序分析
      - 状态信息：重要的状态变化和关键参数
      - 错误上下文：错误发生时的完整上下文信息

3.2 日志内容设计
   - 操作序列：记录操作的开始、进行中、完成状态
   - 数据快照：关键操作前后的数据状态
   - 环境信息：线程ID、连接ID、时间戳等上下文
   - 错误详情：错误码、错误消息、堆栈信息（如果可用）
```

### 4. 测试执行与验证
```
4.1 测试环境准备
   - 清理旧日志：rm -rf logs/ 或使用测试专用日志目录
   - 启动调试模式：确保日志级别为DEBUG
   - 准备测试数据：确保可复现问题的测试用例

4.2 测试执行策略
   - 单步调试：逐步执行测试，观察每个步骤的状态
   - 对比测试：正常情况 vs 问题情况的对比
   - 压力测试：在高负载下复现问题
   - 边界测试：在边界条件下测试

4.3 日志分析方法
   - 时序分析：查找时间戳异常或操作顺序错误
   - 状态追踪：跟踪关键状态的变化过程
   - 数据一致性：验证数据在节点间的一致性
   - 资源使用：监控内存、CPU、网络资源的使用情况
```

### 5. 架构层面分析
```
5.1 Master-Worker交互分析
   - 注册流程：Worker注册、认证、状态同步
   - 心跳机制：心跳发送、接收、超时处理
   - 任务分配：任务选择、Worker匹配、结果收集
   - 错误处理：连接断开、任务失败、重试机制

5.2 数据流分析
   - 存储访问模式：Database创建、读写、冻结操作
   - 数据传递：任务输入输出、Worker间数据共享
   - 元数据管理：任务状态、Worker状态、数据位置

5.3 并发与同步
   - 线程安全：共享资源访问控制
   - 事件处理：异步消息处理机制
   - 依赖管理：任务依赖图的构建和解析
```

## 具体调试场景

### 场景1：Worker无法连接到Master
```
1. 问题表现：Worker启动后无法连接到Master
2. 多维度分析：
   - 网络层：检查端口、防火墙、连接状态
   - 日志层面：查看master.log中的连接信息，worker.log中的连接尝试
   - 配置层面：检查Master和Worker的网络配置
3. 日志增强：
   - Master添加：accept失败日志、连接状态日志
   - Worker添加：连接尝试日志、错误详情日志
4. 测试验证：
   - 使用telnet/netstat检查网络连通性
   - 运行网络测试用例
   - 检查日志中的连接时序
```

### 场景2：任务执行失败
```
1. 问题表现：任务在Worker端执行失败
2. 多维度分析：
   - 任务层面：检查任务参数、依赖关系
   - 数据层面：检查输入数据完整性、输出位置
   - 执行层面：检查Python环境、模块加载、异常处理
3. 日志增强：
   - Worker添加：任务开始/结束日志、异常详情日志
   - 添加任务执行环境信息
   - 记录任务输入输出的完整信息
4. 测试验证：
   - 单独运行任务代码
   - 检查依赖数据是否存在
   - 验证Python模块导入
```

### 场景3：数据同步问题
```
1. 问题表现：多个Worker间的数据不一致
2. 多维度分析：
   - 存储层面：检查数据写入位置、备份状态
   - 网络层面：检查数据传输、复制操作
   - 时序层面：检查操作的并发性和顺序性
3. 日志增强：
   - 添加数据操作的完整日志
   - 记录数据位置和复制状态
   - 跟踪数据访问模式
4. 测试验证：
   - 运行一致性测试
   - 检查数据文件状态
   - 验证元数据一致性
```

## 日志模板与最佳实践

### 标准日志格式
```
[时间戳] [级别] [组件] 消息内容
[2026-05-16 14:30:45.123] [INFO] [MasterAgent] Worker 1 registered successfully
[2026-05-16 14:30:45.456] [DEBUG] [WorkerAgent] Starting task execution
[2026-05-16 14:30:46.789] [ERROR] [Network] Connection timeout to worker 2
```

### 关键日志点
```
MasterAgent关键点：
- Worker注册/断开连接
- 任务分配和调度
- 心跳处理和状态更新
- 数据库注册和路径管理

WorkerAgent关键点：
- 连接到Master
- 任务开始/结束记录
- 数据读写操作
- 心跳发送状态
- 写入跟踪记录

Network关键点：
- 连接建立/断开
- 消息发送/接收
- 错误处理和重试
- 网络状态变化
```

### 日志级别使用指南
- DEBUG：详细的调试信息，用于问题定位
- INFO：关键状态变化，用于流程追踪
- WARN：潜在问题，需要关注但不影响运行
- ERROR：错误状态，需要立即处理

## 调试工具使用

### 1. 日志分析工具
```bash
# 查看Master日志
tail -f logs/master.log

# 查看特定Worker日志
tail -f logs/worker1.log

# 搜索特定错误
grep "ERROR" logs/*.log

# 按组件过滤日志
grep "MasterAgent" logs/*.log

# 按时间范围查看日志
sed -n '2026-05-16 14:30/,2026-05-16 14:35/p' logs/master.log
```

### 2. 测试执行工具
```bash
# 运行特定测试
./fly.sh test //src/agent/tests:agent_network_test

# 运行所有测试
./fly.sh test //src/...

# 运行集成测试
./fly.sh test //src/agent/tests:test_agent_integration

# 清理并重新测试
rm -rf test_logs/ && ./fly.sh test //src/...
```

### 3. 网络调试工具
```bash
# 检查端口占用
netstat -tlnp | grep :19080

# 测试网络连通性
telnet localhost 19080

# 抓包分析
tcpdump -i lo port 19080 -w network.pcap
```

## 禁止的做法
- ❌ 仅通过代码静态分析推测问题
- ❌ 跳过日志收集直接修改代码
- ❌ 在没有日志的情况下进行调试
- ❌ 忽略分布式架构的特性
- ❌ 过度依赖单点调试，忽略系统整体状态

## 成功调试的标准
1. 问题的根本原因被准确定位
2. 修改后的代码在完整测试中通过
3. 日志记录覆盖所有关键路径
4. 不会引入新的问题
5. 调试过程可重复和验证
